# Migrations 0034 and 0035 Rollout

## Deployment Ordering

1. **Order:** Run database migrations (`0034-add-step-revert-counts.ts` and `0035-add-job-resume-disposition.ts`) **before** restarting workers.
2. **Rationale:** These migrations add columns with `DEFAULT` values. If the DB is migrated first, old workers holding leases will continue writing rows without the new columns, and the database will safely apply the default values. When workers are restarted, they can safely read the populated defaults. A worker holding a lease across the migration boundary either drains cleanly or fails safe.

## Rollback Instructions

**`0034-add-step-revert-counts.ts`:** Downgrade the worker binary and restart. The new `revert_counts` column has no `NOT NULL` constraint, so old workers simply ignore it. Strict database rollback (SQLite `ALTER TABLE DROP COLUMN`) is not required but can be performed safely while workers are stopped if desired.

**`0035-add-job-resume-disposition.ts`:** Same procedure — downgrade the worker binary and restart. The new `resume_disposition` column has no `NOT NULL` constraint, so old workers ignore it. Strict database rollback is optional, same caveat as above.

(See #974 and #977 for the exact column definitions if you need to script either downgrade.)

## Reading the Kill Switch's Enforcement Mode After the Fact

`features.scopeContractEnforcement` is part of the resolved config that `config_fingerprint` hashes (`sha256OfCanonicalJson` over the full normalized config in `packages/shared/src/config/loader.ts`), so toggling it changes the fingerprint recorded on every run. There is no dedicated `scope_contract_enforcement` column — the fingerprint is the carrier by design.

To determine which enforcement mode a specific past run used:

1. Look up that run's `config_fingerprint` (and `config_sources_json`, which records which config files were present) in the `runs` table.
2. Find the `.ai-orchestrator.json` content as of that run's `started_at` timestamp (`git log -p --before=<timestamp> -- .ai-orchestrator.json` in the target repo) and read `features.scopeContractEnforcement` directly from that version.
3. If you need to confirm the fingerprint itself rather than trust the file content, recompute `sha256OfCanonicalJson` over that historical config and compare — but reading the flag directly from the versioned config file is normally sufficient and much simpler.
